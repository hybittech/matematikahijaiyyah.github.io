The earlier run predates the memory rewrite in hcpu_dataram.v and
hcpu_memory.v, where both arrays moved from a combinational read to a
registered one. Read the two columns together: cells fall by 20% while
flip-flops barely move, and that split is the whole result.

An asynchronous read needs a multiplexer tree wide enough to select any
word in the array. Registering the read deletes that tree — which is the
96,000 cells — but the storage itself has nowhere better to go in this
flow, because no memory primitive exists to map it to. Generic gates
offer flip-flops and nothing else.

The same change measured against a real memory library tells the other
half. Synthesised for the Tang Nano 9K (synth_gowin, top =
hcpu_gowin_top), the design now maps its arrays to block RAM:

  LUT           3,053  of  8,640
  Flip-flops    1,646  of  6,480
  BSRAM blocks      4  of     26

So the fix works; this report simply cannot see it. Any ASIC number
below carries the same caveat until the design is synthesised against a
PDK with an SRAM macro.

Reading the numbers
-------------------
1. hcpu_dataram still dominates at 4096 words x 32 bits = 131,072 bits,
   and still becomes flip-flops here for want of a memory macro. Its
   cell count fell 35% (416,165 -> 270,568) with the flip-flop count
   unchanged: that is the read multiplexer leaving, not the storage.

2. hcpu_memory's stack behaved the same way — 25,480 -> 17,443 cells
   over 8,4xx flip-flops. Both arrays were changed for the same reason
   and moved the same way.

3. hcpu_codex_alu grew (12,135 -> 15,069) and hcpu_top grew sharply
   (700 -> 7,093). The top-level figure is the larger part of the
   difference and is a boundary effect: this run counts modules before
   technology mapping, where the earlier one counted after, so logic
   that ABC later hoists or absorbs is still attributed to hcpu_top.
   Treat the per-module column as indicative and the design total as
   the measurement.

4. Longest topological path: 86 logic levels, from \print_val — the
   divide- and modulo-by-10 in the PRINT FSM at hcpu_top.v:193-194,
   the same path the previous run found. It is a timing concern, not
   an area one.

   A hand-written shift-add reciprocal was tried in its place and
   measured worse on both counts under synth_gowin: 10,836 LUTs against
   8,871, and a longest path of 1,149 against 927. Yosys already lowers
   division by a constant into a better circuit than the textbook
   trick, so the obvious optimisation is a pessimisation. The `/ 10`
   and `% 10` stay, and hcpu_top.v carries a comment saying why.

Caveats
-------
* No SKY130 PDK is installed, so these are generic-gate counts, not
  mapped standard cells, and no um^2 area or ns timing can be derived
  from this run. Cell counts are indicative of relative size only.
* Any die-area figure requires re-running with a liberty file.
* 131,072 flip-flops will not fit the 700x700 um user area in
  config.json. That remains true, and remains the reason claims of MPW
  readiness are withheld.
* Re-run against the real PDK to obtain area and timing closure. The
  first step is mapping hcpu_dataram to an SRAM macro from the
  foundry's memory compiler; until then this report measures a design
  that stores 16 KB in flip-flops.

Reproducing

  cd rtl/mpw && yosys -s synth_hcpu.ys
